# REVIEW.md

Defects found in the starter `app/main.py`. Line numbers refer to the starter file. Every fix is covered by a test in
`tests/test_api.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | module, `MongoClient(...)` (l.22) | Client is not `tz_aware`, so PyMongo returns **naive** datetimes. Mixing them with the aware `IST` values in the helpers raises `TypeError`, and naive values are easily misread as local time. | `compute_overtime(record["punch_out"], ...)` on a stored record -> `TypeError: can't subtract offset-naive and offset-aware datetimes` -> 500. | `MongoClient(..., tz_aware=True, tzinfo=UTC)`; all instants are aware UTC internally and converted to IST only for rule maths. |
| 2 | module / startup | **No indexes are created.** `emp_code` is not unique, `(emp_code, date)` is not unique, and every list/analytics query is a `COLLSCAN`. | `db.employees.index_information()` only shows `_id_`; explain shows `COLLSCAN` at 100k docs. | `ensure_indexes()` in the FastAPI lifespan (idempotent `create_index`), retried from `/health` if MongoDB was not up at boot. See DECISIONS.md. |
| 3 | `compute_late_minutes` (l.35) | `punch_in.replace(hour=h, minute=m)` overwrites the fields of a UTC (or server-local) value instead of **converting to IST** first, so the shift start is in the wrong time zone. | Punch at 09:45 IST = 04:15Z. `replace` gives 09:30Z as the start, so the difference is negative and late = 0 (should be 15). | Shift start is built as `datetime.combine(attendance_date, shift_start, IST)` and compared with the aware instant. |
| 4 | `compute_late_minutes` (l.37) | Grace check is `minutes > 10` on **already-floored** minutes, so anything from 10:01 to 10:59 after start counts as on time. R2 says strictly more than 10:00. | Shift 09:30, punch 09:40:01 -> `int(10.02)=10`, `10 > 10` is false -> 0 (expected 10). | Compare **seconds**: `seconds > 600`, then `seconds // 60`. |
| 5 | `compute_late_minutes` | Overnight shifts are ignored: a punch-in after midnight belongs to the shift that started the previous day (R1). | Shift 22:00-06:00, punch 00:40 IST -> start computed as 22:00 the same day -> negative -> 0 (expected 160). | `attendance_date()` implements R1 and `shift_window(day, emp)` gives the start on that day. |
| 6 | `compute_work_hours` (l.41) | `round(x, 2)` is float/banker's rounding, not half-up (R4). Instants are not truncated to seconds (R1). | 4h 00m 18s = 4.005 h -> `round` gives **4.0**, expected **4.01**. Also changes `half_day` around 4.50. | `Decimal(seconds) / 3600` quantized with `ROUND_HALF_UP`; inputs truncated to whole seconds. |
| 7 | `compute_overtime` (l.47) | No 30-minute minimum (R3). | Punch-out 18:35 on an 18:30 shift -> 5 (expected 0). | Return the minutes only if `>= 30`. |
| 8 | `compute_overtime` (l.46) | For overnight shifts the shift end is put on the **same** date as the shift start instead of the next day. | Shift 22:00-06:00 dated 07-06, out 06:40 on 07-07 -> 1480 min (expected 40). | `shift_window()` moves the end to the next day when `shift_end <= shift_start`. |
| 9 | `EmployeeIn` (l.53) | No validation: any `emp_code`, email, shift time or date is accepted, and `shift_start == shift_end` is allowed. | `POST /employees` with `emp_code: "x"`, `shift_start: "25:99"`, `joined_on: "2026-02-30"` -> 201. | Pydantic constraints from the contract (`^EMP[0-9]{4,6}$`, lengths, email and `HH:MM` patterns, real `YYYY-MM-DD` date) plus a model validator for distinct shift times. |
| 10 | `create_employee` (l.79) | **Check-then-insert race**: two concurrent creates both pass `find_one` and both insert. | 10 parallel identical POSTs -> several 201s and duplicate employees. | Unique index on `emp_code`; insert directly and map `DuplicateKeyError` to 409. |
| 11 | `create_employee` (l.82) | `datetime.now()` is naive **local** time; PyMongo stores it as if it were UTC (5h30 off on an IST server). The response returns a datetime, not epoch ms. | On an IST machine `created_at` is 5h30m in the future; the response has `"created_at": "2026-...T..."`. | `datetime.now(UTC)` (truncated to ms, which BSON keeps), returned via `to_ms()`. |
| 12 | `list_employees` (l.93) | `skip = page * page_size`: page 1 skips the first page. | 25 employees, `?page=1` returns employees 21-25. | `skip = (page - 1) * page_size`. |
| 13 | `list_employees` (l.94) | `total` counts the whole collection, ignoring the department filter (R10). | `?department=Sales` -> `total` = all employees. | `count_documents(query)` with the same filter. |
| 14 | `list_employees` (l.95) | No sort; the contract says `emp_code` ascending. Order is otherwise unspecified and can change between pages. | Insert EMP0005 before EMP0001 -> it is listed first. | `.sort("emp_code", 1)` (served by the unique index). |
| 15 | `list_employees`, `list_attendance` | `page` / `page_size` are not bounded (R10). `page=-1` -> negative skip -> 500; `page_size=0` -> `limit(0)` means **no limit**; `page_size=100000` dumps everything. | `GET /employees?page=-1` -> 500. | `Query(ge=1)` and `Query(ge=1, le=100)` -> 422. |
| 16 | `list_employees` | `_id` was projected out, but `created_at` is returned as a datetime string, not epoch ms. | Response field type mismatch against the contract. | `employee_out()` serializer. |
| 17 | `PunchInIn.punched_at` (l.65) | `Optional[int]` in lax mode accepts **seconds**-looking values, floats (`1.7e12`), numeric strings, booleans and `null`; and `if body.punched_at` treats an explicit `0` as "now". | `{"punched_at": 1783312500}` (seconds) creates a record dated 1970-01-21; `"1783312500000"` is accepted. | `Annotated[int, Field(strict=True, ge=100000000000, le=4102444800000)]` -> 422. |
| 18 | `PunchInIn.status` (l.66) | Free string: `ABSENT`, `LEAVE` or `"foo"` can be punched in. | `{"status": "LEAVE"}` -> 201 with a punch time. | `Literal["PRESENT", "WFH", "ON_DUTY"]`. |

| 20 | `punch_in` (l.102) | `datetime.fromtimestamp(ms / 1000)` uses the **server's** time zone and returns a naive value: the attendance `date`, the late calculation and the stored instant all depend on where the server runs. | 21 | `punch_in` (l.103) | R1 overnight rule missing: date is always the calendar date. | 22:00-06:00 shift, punch 00:40 IST -> dated the next day, so the punch-out cannot find the right shift. | `attendance_date()`. |
| 22 | `punch_in` (l.104) | **Check-then-insert race** on `(emp_code, date)`. | 10 parallel identical punch-ins -> several 201s and duplicate records. | Unique `(emp_code, date)` index; insert and map `DuplicateKeyError` to 409. |
| 23 | `punch_in` response (l.119) | Leaks the internal `_id` as `id`, and returns datetimes instead of epoch ms. | Response has `"id": "66a..."` and `"punch_in": "2026-..."`. | `record_out()` serializer (contract fields only, instants as ms). |

| 27 | `list_attendance` params | Dates and status not validated; `date_from > date_to` not rejected. | `?status=foo` or `?date_from=2026-07-10&date_to=2026-07-01` -> 200 with nothing. | `DateStr` validator, `Status` literal, explicit 422 for an inverted range. |

### Looked at and decided were **not** defects

* `load_dotenv()` with default `override=False`: real environment variables already win over `.env`, as required.
* `IST = timezone(timedelta(hours=5, minutes=30))` is correct (no DST in India).
* `int(...)` truncation in the helpers is the same as floor for the non-negative values it matters for, so it is not wrong by itself (the bugs above are what it is applied to).
* `doc.pop("_id", None)` after `insert_one` is needed, because PyMongo adds `_id` to the dict it inserts. It is kept, in spirit, by serializing through `record_out()` / `employee_out()`.
* Comparing `date` strings with `$gte` / `$lte` is correct: `YYYY-MM-DD` sorts lexicographically in date order.
* Sync `def` endpoints with sync PyMongo are fine: FastAPI runs them in its thread pool, so they do not block the event loop.
* `status_code=201` on the two create endpoints matches the contract.
